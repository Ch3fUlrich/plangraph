# V1 WAL data loss

**Checkpoint and delete logic in section 3 is correct.** The compound gate:

```
{ [ ! -s WAL ] || python3 -c "...wal_checkpoint(TRUNCATE)...raise SystemExit(r[0])"; } \
  && [ ! -s WAL ] && echo OK || { echo FAIL; false; }
```

Under `bash -eo pipefail`, `false` as the last command of the `||` branch returns 1 for the whole and-or list; since the list's exit status IS the status of the last executed command, errexit fires and the script halts before the rm or the chmod. The unit is already stopped (section 2) so no writer can race the TRUNCATE checkpoint. The re-test `[ ! -s WAL ]` after the checkpoint is the gate before `rm -f`: only a missing or 0-byte WAL reaches the rm (a 0-byte WAL has no committed frames). No non-empty WAL is ever deleted.

**Section 2 backup covers all committed frames.** `s.backup(d)` uses SQLite's online backup API with source opened `mode=ro` — the API folds WAL content into the destination file regardless of checkpoint state. This happens before the section 3 fingerprint.

**sha256 covers a complete database.** After TRUNCATE, all WAL frames reside in `keeper.db`; WAL is 0. `sha256sum $LIVE/keeper.db` after the chmod captures the entire committed dataset. Evidence: file `keeper-pg-cutover.md` section 3, lines: `chmod 0400` → `sha256sum`.

**Section 7 rollback WAL guard:** `[ ! -s WAL ] || { echo ...; false; }` — same errexit reasoning; non-empty WAL halts the script before any rm or chmod. Correct.
