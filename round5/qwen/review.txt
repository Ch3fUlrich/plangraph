## V1: Migration Safety

**Idempotency is adequate for DDL, but has gaps.**

`db._upgrade` (src/plangraph/keeper/db.py) runs five sequential `conn.executescript` calls plus a final `_upgrade_lock_triggers(conn)`. Each `executescript` in Python's sqlite3 with `isolation_level=None` auto-commits independently. The doc correctly acknowledges "open_db runs several idempotent scripts without one enclosing transaction" (sec 4 step 5). All CREATE statements in DESIGN3_DDL (src/plangraph/keeper/schema.py) use `IF NOT EXISTS`, confirmed by the three successful re-runs of `admin migrate` in the dry run.

**Defect: `_upgrade_lock_triggers` has no code excerpt and its idempotency cannot be verified.** The doc does not mention this function at all in section 1's migration summary. If it uses `CREATE TRIGGER` without `IF NOT EXISTS`, a re-run would raise `OperationalError`. Speculation level: the dry run started the daemon (which calls `_upgrade`) three times on different copies without error, so this was exercised at least three times—but only on an already-migrated schema. A fresh f3bac63 db with partially-migrated state was never tested.

**Lock/concurrency is correctly ordered.** `daemon.run` (src/plangraph/keeper/daemon.py) calls `lock_keeper` before `open_db`, so the flock is held during migration. The doc correctly notes single-writer-under-lock. WAL mode with `busy_timeout=5000ms` (`_DEFAULT_BUSY_MS`) protects against other sqlite3 connections that skip the flock, but the doc's prohibition ("do NOT run pg admin migrate against live db while daemon runs") is the right operational guard.

**Backup procedure:** `.backup` (not `cp`) is mandated for WAL safety. The doc is correct: `sqlite3.Connection.backup` checkpoints the WAL into the copy atomically.

## V5: Restart Runbook

**Defect 1 — Internal contradiction on `pg admin` vs. daemon-up.** Step 4 instructs: "Verify: `pg admin verify` = chain and cache integrity ok." Step 5 then states: "Never run any `pg admin` command (migrate included) while the daemon is up; check `systemctl --user is-active plangraph-keeper` first." These directly conflict. The dry run shows `admin verify` succeeding with the daemon up (it likely opens a separate read-only connection or hits the API). The runbook must either: (a) carve out read-only commands from the prohibition, or (b) instruct stopping the daemon before verify (which would mean stopping a freshly-started production service to run a check that could be done while it's up).

**Defect 2 — No client-quiesce step before backup.** Step 2 stops the daemon and backs up. But between the last WAL checkpoint (at stop) and the backup file being written, there is a window. `.backup` on a stopped db is safe because no writer exists. However, the doc does not explicitly state the daemon must be fully exited (not just SIGTERM sent). With `Restart=on-failure`, if the process dies from a signal other than a clean exit before the backup completes, a new process could grab the lock and start writing. The doc says "confirm with `is-active` and that no process holds keeper.db.lock: `fuser keeper.db.lock` prints nothing" — but this confirmation is only mentioned in the abort/restore path (step 5b), not in step 2.

**No step harms the live db directly.** The backup uses `.backup` (WAL-safe), the stop is explicit, the unit edit is before start. Good.

**Abort ordering (step 5a-e) is sound** — stop, confirm no process, delete WAL/SHM before placing the pre-migration backup, restore config, repoint unit, start, verify. The WAL-deletion-before-restore step correctly prevents a half-migrated WAL from corrupting the restored db.

**Missing abort criterion:** If the daemon starts but the reaper or outage check crashes it, the unit's `Restart=on-failure` would loop. The doc's abort trigger "daemon exit/restart loop" is listed but there is no explicit step to prevent the restart loop (e.g., `systemctl stop` after first failure, or editing `Restart=` temporarily). The operator must notice and act.
