**V1 – Migration safety**

*Evidence*  
- `src/plangraph/keeper/db.py:open_db` obtains the exclusive lock via `kdb.lock_keeper` **before** calling `_upgrade` (`daemon.run` → `lock_keeper` then `open_db`).  
- `src/plangraph/keeper/db.py:_upgrade` iterates over `_ADDED_COLUMNS` and runs `ALTER TABLE … ADD COLUMN` only when the column is absent, then executes a series of `executescript(... IF NOT EXISTS ...)` for all new tables, triggers and projector DDL.  
- The function comment explicitly states “Add any column/table/trigger an older database lacks; **idempotent, DML‑free**”.  
- PRAGMA settings (`journal_mode=WAL`, `busy_timeout`) are applied before the migration, and the backup procedure in the runbook uses `sqlite3.Connection.backup`, which folds the WAL safely.

*Assessment*  
The migration runs under the keeper lock, so no concurrent writers can interleave. All schema changes are idempotent and do not modify existing rows, eliminating data‑loss risk. The only non‑atomic element is the series of separate `executescript` calls, but each statement is `IF NOT EXISTS`, so a half‑finished run leaves the database in a state that a subsequent start can finish safely (the runbook explicitly mentions the “half‑migration” retry). No defect identified.

**V3 – Dry‑run coverage**

*Evidence*  
- The dry‑run log exercises read verbs, basic write verbs, the new `state_set` path, and the new `/v1/*` HTTP endpoints.  
- Unexercised paths listed in the DOC: **Postgres backend**, **backup_prune thread**, **Temporal‑enabled signal path**, **append‑only triggers for attempts/decisions/answers** (update/delete), and higher‑level verbs `rehome`, `delegate`, `token`, etc.

*Defect / uncovered risk*  
1. **backup_prune thread** – The daemon can start the optional `backup_prune` background thread (config key `backup_prune.enabled`). This path is not exercised in the dry‑run; if the configured backup directory is missing or permissions are wrong, the thread could raise uncaught exceptions and crash the daemon.  
2. **Non‑atomic migration** – `_upgrade` runs several `executescript` calls outside a single transaction. Although each statement is `IF NOT EXISTS`, a sudden termination (e.g., OOM or disk‑full) could leave the database with a partially applied set of DDL objects. The runbook mentions restarting to complete the migration, but does not verify that the daemon correctly detects and recovers from an **OperationalError** caused by a missing object, which could result in a start‑up failure that is not automatically retried.  

*Log explanation* – All rc ≠ 0 entries in the dry‑run log are correctly explained in the DOC (e.g., `changelog rc=2` → missing `--since`; `admin verify‑snapshot rc=1` → empty snapshot path; initial `define` failure → unreachable goal). No discrepancy found.
