**Is the check query right?**

```sql
select count(*) from keeper.events where type=$$item_reopened$$
```

`$$...$$` is PostgreSQL dollar-quoting — syntactically valid and equivalent to `type = 'item_reopened'`. It avoids nested-quote escaping issues in the shell layer (`\$\$` produces literal `$$`). The column `type` is the indexed event type TEXT column. Correct.

**Does the runbook order hold together?**

1. Worktree prep (no live impact)
2. Pre-checks + counts baseline + reopen-window check (must be 0)
3. Pre-GO dump (insurance, no stop — schema is unchanged)
4. Migration no-op check (owner, BEFORE restart — catches any surprise)
5. Drop-in (file placement; no restart yet)
6. Restart + env check
7. Verify gates including counts-diff and reopen-window re-check
8. Rollback only if gates fail AND reopen-window is still 0

The critical ordering property: step 4 (migrate check) runs before step 6 (restart), so if the schema unexpectedly needed migration the old keeper is still running and no data loss occurs. The dump is taken at step 3 before any code change. The gates at step 7 are the last moment to roll back safely. Normal traffic between dump and restart is covered because rollback doesn't restore the dump — it restarts the old code, which reads all rows including those written between steps.

**One observation**: the packet says "no writes in between except normal traffic: if live traffic wrote, expect only growth, never shrinkage; events must be >= pre." This is correct for the append-only event model. Items could gain new ones but never lose them.
