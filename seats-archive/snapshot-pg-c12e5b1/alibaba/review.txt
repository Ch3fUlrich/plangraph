V3 staleness vs consumers — BOUND IS REAL under successful builds, breaks under repeated failures.
- Live‑DB consumers (`GET /v1/snapshot`, md‑sync, `pg render`, `api._snapshot`'s request path now only marks) are unaffected — always current.
- File consumers (`snapshot_serve`/`snapshot_pull`, `cli_verbs.local_snapshot`, `pg admin verify-snapshot`) read a lagged file. For a steady write stream the cap is honored: `run` uses `due = min(_last+debounce, _first+max_delay)` and `_first` is fixed from the oldest unwritten mark until a build clears it, so a build fires within `max_delay`; because `_write_locked` re‑arms `_first=_last=now` whenever `_written != _gen` after a build, the true bound is `max_delay + one build`, matching the doc.
- Caveats: each failed build re‑arms `_first=now` and backs off one debounce, so N failures add ~N·debounce; under persistent failure `max_delay` is exceeded without bound. `admin verify-snapshot` only checks file↔sig consistency, not DB currency, so a stale‑but‑self‑consistent file "verifies" green — staleness for file readers is policed only by `snapshot_pull.behind_mark`. Also the `audit_log` row now attributes to `system` once per rebuild instead of the writing principal per write — audit fidelity for "who moved the snapshot" is reduced (documented).
