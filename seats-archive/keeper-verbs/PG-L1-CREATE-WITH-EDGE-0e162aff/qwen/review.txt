## V1 — Auth: `_under_gate` and `_create`

**PASS.**

- `_under_gate` calls `self._may_manage(principal, gate["project"])` before anything else, so a caller that cannot manage the gate's project is refused (`forbidden`). Then the cross-project guard: `principal.role != "router" and gate["project"] != definition["project"]` → `forbidden`. The `gate["project"]` value comes from the database row returned by `_get_or_refuse`, not from the caller-supplied string, so alias/qualify tricks cannot fabricate a project that bypasses the check.
- `store_input.py:_normalise` resolves `under` via `self._qualify(project, under)` — same qualification path as `fixes`/`corrects`/`depends_on` — yielding a fully-qualified key that is then looked up in the database. No way to inject a project string that survives into `_under_gate`'s comparison.
- Role check for `create_items` (router/l1 only) is enforced by `_run` verb dispatch **before** `_create` is entered. Roles like worker, reviewer, reader, system are refused (`forbidden`) — confirmed by `test_roles_that_may_not_create_cannot_attach`. No write occurs because the lambda is never reached.
- `_assert_unlocked(gate)` covers locked gates separately from done/cancelled (`bad_state`).

## V2 — Atomicity: gate resolution, graph validation, and write block

**PASS.**

- All pre-flight checks (batch size, legacy `under` rejection, `_normalise`, kind/state validation, conflict/exists, `_under_gate` × N, candidate-graph mutation, `_validate_change`) complete **before** the `with self._write():` block. No database mutation is attempted if validation raises.
- Inside the write block, every gate is re-checked via a guarded `UPDATE ... WHERE key=? AND state=? AND epoch=?` followed by `self._row_guard(cursor, ...)`. If another transaction moved the gate to done/cancelled/locked between the read and the write, the UPDATE affects zero rows, `_row_guard` raises, and the context-manager transaction rolls back — no items, edges, or events survive.
- The `for definition, gate in attach` loop inserts the edge and appends the event for the **same** gate atomically (same transaction). Multiple items under the same gate are handled correctly: the WHERE clause uses `state`/`epoch` (unchanged by a prior `updated_at` touch in the same transaction), so each guarded UPDATE matches.
- `_validate_change` is called on a `candidate` that includes the mutated gate `depends_on` entries and both the pre-existing items (`before`) and the new `defs`, with `affected` containing both new keys and touched gate keys. A cycle (e.g. `deps=["GOAL"], under="GOAL"`) or stranded item is caught before the write.
