# HIGH-style Security Review — env-driven mTLS for Temporal connection

## V1 Fail-open
No env/config combination silently downgrades an intended-TLS connect:
- `tls_from_vars` (rust/worker/src/tls.rs) folds empty/whitespace-only values into "unset" (`setting` closure with `trim()` + `filter(!is_empty())`), so `VAR=` cannot half-enable TLS. All unset ⇒ `Ok(None)` = plain connect, which is the documented, unchanged baseline — an opt-in, not a silent fallback from an intended TLS state.
- Partial CERT/KEY/CA set ⇒ hard `Err` naming missing vars, before any file read; SERVER_NAME alone (with all three unset) ⇒ hard `Err`. Covered by `cert_alone_is_refused`, `cert_and_key_without_ca_is_refused`, `server_name_alone_is_refused`.
- CA is mandatory whenever TLS is on: there is no env combination that yields `TlsOptions` without `server_root_ca_cert`, so the "system-roots-only" and "unauthenticated TLS" states are unreachable through this helper. `client_tls_options` is always `Some`, so no server-only-TLS-without-client-cert state either.
- `http://` URL + TLS vars ⇒ `require_https` refuses at startup in all three binaries (`tls.is_some() && !addr...starts_with("https://")`), case-insensitively; `https_with_tls_is_accepted` / `http_with_tls_is_refused` / `http_without_tls_stays_plain` pin the rule.
- Residual (design-level, not a defect of this diff): there is no "TLS required" enforcement switch, so if the three env vars are accidentally lost in a deployment, the worker silently connects plaintext. This is the documented HIGH-style opt-in contract (TLS.md), but a deployment-side guard would strengthen it. LOW/observation.

## V2 Secret handling
Clean within this code:

## V3 Server verification
- CA bytes are passed via `server_root_ca_cert`, and the handshake check (`rust/tls-handshake-check.sh`) behaviorally proves verification: wrong CA is refused, and wrong server name is refused (`run otherca.crt` / `run ca.crt wrong.test` asserting the server never logs "depth=0 CN = client", i.e. handshake fails before client-cert presentation is accepted).
- No insecure/skip-verify option is set or exposed; there is no path that builds `TlsOptions` without the CA, so accidental system-roots-only verification is impossible here.
- Caveat: the "wrong server name refused" test conflates any handshake failure with name-verification failure (a timeout would also pass the assert), and the SDK's exact use of `domain` (SNI + SAN match, per TLS.md "set SERVER_NAME to a SAN when connecting by IP") is external behavior I can only vouch for via that script. Adequate, with the noted imprecision.
