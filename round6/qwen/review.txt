## V1 migration safety

The doc's core claim is grounded and holds. In `db.py:open_db`, the non-create path checks that the `items` table exists and then calls `db.py:_upgrade`, which only does `ALTER TABLE ... ADD COLUMN` guarded by a `PRAGMA table_info` membership check (`db.py:_ADDED_COLUMNS`) plus `executescript` of DDL that the doc and `schema.py:DESIGN3_DDL` describe as `CREATE TABLE/TRIGGER IF NOT EXISTS` and DML-free. The doc's statement that `_ADDED_COLUMNS` is unchanged and no existing table is altered is consistent with the excerpt.

Concurrency and lock: `daemon.py:run` acquires `kdb.lock_keeper` (the `keeper.db.lock` flock) before `open_db`, so migration runs single-writer; the doc correctly warns not to run a writing `pg admin migrate` while the daemon is up. `busy_timeout` default is `_DEFAULT_BUSY_MS = 5000`, matching the doc. Idempotent re-runs are supported by `IF NOT EXISTS` and the dry-run log showing three successful `admin migrate` runs with no error.

Defect (grounded): the doc's section 1 says "No existing table altered; no ALTER on existing columns; `_ADDED_COLUMNS` unchanged" is fine for T, but the excerpt shows `db.py:_upgrade` iterates `_ADDED_COLUMNS` with `ALTER TABLE items ADD COLUMN ...` (description/host/wait/writer_model/seat_models). These are additions of *nullable* TEXT columns to a populated `items` table; SQLite permits this and it is not data loss, so this is safe — noting for completeness, no defect.

Backup procedure is sound: doc mandates `sqlite3.Connection.backup` (WAL-safe) after a confirmed stop, which folds the WAL; `db.py:open_db` sets `PRAGMA journal_mode=WAL`, so a plain `cp` would indeed miss `-wal`/`-shm` and the doc correctly forbids it.

## V5 restart runbook (doc section 4)

Ordering is coherent and grounded: stop → confirm `is-active`=inactive and `fuser keeper.db.lock` empty → `.backup` → swap unit → start (migration in `open_db` under lock) → verify. This matches `daemon.py:run` lock-then-open and the WAL note.

Defect (harm to live db) — restore step (b): "delete keeper.db-wal and keeper.db-shm from the data dir BEFORE placing the backup." Deleting `-wal` before `-shm`/db copy is generally fine, but this step deletes files *only in the abort path*, and the doc correctly says a leftover WAL must not meet the restored db. However, in step 2 the doc already folds the WAL via `.backup` on a *stopped* db; that is safe. The one hazard: `fuser keeper.db.lock` checks the lock file, but `db.py` opens the *db* path; if a stale process still holds the db open (not just the lock) after `is-active`=inactive, deleting WAL could lose committed-but-unfolded pages. The doc mitigates by requiring the process stopped first — acceptable, flagged as residual risk.

Defect (correctness of half-migration recovery, step 5): "several idempotent scripts without one enclosing transaction; if killed mid-start, start again; missing-table OperationalError = start again once." This is grounded in `db.py:_upgrade` using separate `executescript` calls with `IF NOT EXISTS`, so partial migration is recoverable — but only because each DDL is individually idempotent. It holds. However `conn.execute("PRAGMA journal_mode=WAL")` and the `ALTER TABLE ADD COLUMN` (in `_upgrade`) are NOT wrapped by `IF NOT EXISTS` for the column — they rely on the `PRAGMA table_info` guard, which is correct. No defect.

Abort criteria ("any verify failure, daemon loop, or original row disappearing") are reasonable and match the invariant (no original row disappears; counts >= backup). `store_cards.py:_set_state` never deletes items (UPDATE only), so "original row disappears" would indicate a real problem — consistent.

One runbook-vs-code tension: step 4 relies on `pg admin verify` "chain and cache integrity"; `db.py:open_db` sets `PRAGMA trusted_schema=OFF` and `_enable_defensive`, which could restrict triggers during `verify` on the live (larger) db, but verify ran fine on copies — not proven to differ on live, so speculation.
