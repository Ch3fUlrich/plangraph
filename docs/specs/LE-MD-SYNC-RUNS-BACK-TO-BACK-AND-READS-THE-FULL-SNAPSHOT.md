# LE-MD-SYNC-RUNS-BACK-TO-BACK-AND-READS-THE-FULL-SNAPSHOT

Outcome. Make scheduled Markdown sync read only changed work from Keeper while preserving authoritative atomic closes.

Live: Twelve consecutive scheduled unit activations each finish under 60 seconds end-to-end, including fetch; record elapsed, phase durations, Keeper reads and ops, alert at a run over 300 seconds and reject overlapping imports. An idle activation performs zero Keeper snapshot reads. A single new decision reads only its named targets and necessary aliases. Compare comparable workload and retain results for fallbacks and valid large imports. Activation is separately authorized after protected deployment.

## Decisions

- D1. K2 is staged. No claim or implementation before protected #1323 land, refreshed source base, exact spec/tree/card bindings and independently accepted revised scope. #1323 changes md-sync live-close semantics and the same end-to-end fixture. Check phase-evidence gate below as a separate prerequisite. K1 precedes K2 and they serialize the shared api.py. R and S wait on K.
- D2. Incident: 10-minute calendar timer, approximately 12.9 MB per old full snapshot, mostly zero operations. Fourteen complete retained unit activations include seven starting at or after 12:40Z. Those seven lasted 586–915 s, start to last fetch line consumed 11–16 s, and last fetch line to finish 570–904 s. The bounds are coarse and do not isolate process startup or Git/subprocess timing. No defensible retained unit scope separates snapshot GET, plan and apply. Keeper HTTP timing is not reliably correlated by caller. Before claim furnish a bounded phase receipt for fetch/projection/plan/apply (or record a superseding routing disposition with a prospective baseline plan); a qualitative attribution does not satisfy the current gate.
- D3. Base tools/md_sync.py uses the full snapshot and builds from all D-rows; snapshot_filter currently builds expensive blocks before shaping. README examples are not the loaded timer authority. Scheduled activation belongs to the installed unit and keeps its current OnCalendar=*:0/10. Moving the fetch under scheduled CLI control needs one staged deployment that removes the old ExecStartPre and opts in only after matching Keeper server code is live. Default import and archive continue to use the legacy read/merge paths while the checkout follows main.

## Entry points

- E1. Scheduled-only GET /v1/snapshot?view=md-sync with optional exact keys through authenticated committed Store.snapshot and scoped D-row planning. Default import and archive use their existing Session.snapshot.
- E2. Captured sources to apply_batch.write path and atomic /v1/apply_ops, current Store._close_on_decision, verified origin/epoch/live evidence, and retry.
- E3. Scheduled timer, configured path/manual trigger against the same scheduled lease, selective fetch, status writer, and the unchanged manual and archive commands.

## Scope and reuse

- R1. Add opt-in md-sync-v1 JSON in K2's five-line api.py dispatch allowance. Pass view validation to existing snapshot_filter/Store.snapshot; require a configured independent committed reader and normal snapshot permission. Refuse duplicate/unknown arguments, fmt=text and unparsed keys. No effect on bare snapshot or text requests. X4 pins 60s for narrow all rows (bootstrap/repair/large valid request), 15s for exact-key read. Validate marker and items/alias/head shape. Wrong marker or unavailable view causes the scheduled invocation to fail with no fallback. Existing CLI/manual/dry/archive keep their route and 60s behavior until an explicit scheduled service activation. Use bulk hydration and parameterized SQL constrained to selected canonical item/alias/evidence/dependency keys in targeted mode. Allow at most 32 requested keys and 4 KiB encoded request target; preselect narrow all rows once above either limit. Return only planner fields consumed by both planners, including decision/current-epoch commit evidence and the live-proof fields warranted by #1323. Exclude reviews, fleet, activity, progress, incidents, answers and decision text. Preserve alias behavior and committed head consistency. No API/schema changes for other consumers.
- R2. Capture QUESTIONS, ANSWERS and decisions bytes and verify the three digests immediately before scheduled submit. Feed both canonical parsers from identical frozen decision bytes via DecisionsAdapter.from_text. Existing ANSWERS source pin and Store._close_on_decision remain authority, including commit ancestry, epoch and live proof. A proved input change may rerun read and plan once using freshly captured inputs. Existing known refusal/drop and already-DONE controls still apply only when definitively rolled back. Use current apply_batch transport and atomic transaction unchanged. No base_seq extension, transport callbacks, or permanent blocking operation journal. After an uncertain result stop this invocation, retain previous cursor, and on the next eligible tick require a fresh committed view from the unchanged cursor; recompute from current graph and authoritative checks, never retain or replay an old op list. In-flight server apply and reissued work remain governed by existing state checks and batch atomicity. Preserve the reconciliation diagnostic where the caller cannot establish effects. State-only changes that need an added general transactional fence require a separate demonstrated failing scenario and scope.
- R3. Scheduled requires --apply and --status-file. Take nonblocking flock on the private stable file named by appending .lock to the canonical configured status path, mode 0600; hold from before inputs through cursor/status write, and never unlink. Crash releases lease. A competing tick emits overlap and leaves active run's status alone. Keep the timer calendar schedule; no post-completion cooldown. Move current ExecStartPre fetch after local candidate classification within scheduled CLI. Retain existing legacy helper invocation as compatible no-argument default. Reuse helper with a sorted deduplicated set of relevant (repo, remote) pairs from current/remembered configured GitGates.target, including a known project/track fallback. If first bootstrap needs all configured remotes, the planner marks that explicitly, and a large legitimate operation remains one valid call. Skip fetch when no new work and no merge-pending remote to check. With merge-pending work, refresh only those remotes so an unchanged local remote-tracking ref cannot hide a remote update. Respect existing per-fetch cap, add a shared scheduled fetch phase budget below the 60s goal (30s initial EXPERIMENT), keep pending on failure and report it without treating failed-fetch ref equality as proof. Legacy fetch behavior and defaults stay intact. An authorized installation removes the old ExecStartPre when enabling --scheduled, with exact installed artifact witness before activation.
- R4. Cursor is the canonical scheduled status path with .cursor.json appended, mode 0600, same-directory atomic replace while holding the lease. Persist validated prefix byte length plus SHA-256, source/config hashes, D-row fingerprints for settled targets, and pending D-id/key, relevant primary/track ref identity and SHA, outcome category. On idle matching hashes and unchanged trigger(s), do zero Keeper requests. On append-only include new rows and only prior pending keys with changed source/config/ref (or explicit targeted wake); preserve supersession via related earlier rows from one canonical decision parse and one frozen DecisionsAdapter snapshot; reuse its parsed rows rather than walking the whole decisions file once per unrelated key. Scope the planner's legacy create/answer/gone scan to initial/full reconciliation and when Q/A changed, so partial item sets never drive false creates or gone notices. Commit-only missing/unmerged remains pending and wakes on a ref change. In-review no-sha stays pending until a relevant source/config change. Graph-only flags like deploy evidence, rehome, or corrected grants remain pending and may be retried by explicit --reconcile-pending using the same lease; automatic targeted graph-only wake needs an existing structured delivery signal or a separately approved policy/scope. No periodic broad polling or blind retry. On invalid cursor/input baseline, Q/A/config changes, rewritten/reordered prefix, or above-cap selection, make one narrow all-rows read and preserve legacy semantics. Advance cursor only after confirmed apply or proved no-op; never consume uncertain changes or erase unresolved pending targets. Retain invalid row diagnostics and operate on canonical IDs rather than free-text status parsing.
- R5. Every accepted scheduled run emits fixed status and duration fields for fetch, Keeper read, plan and apply, total seconds, read count and op count. Monotonic clock and known phase entry/exit; skipped phases record zero with explicit read mode. Emit the slow-run warning when elapsed >300 s, including error exits; preserved status keeps prior fields and atomic file replacement. Keep telemetry payload-free. Define separately reported full unit duration including process startup.
