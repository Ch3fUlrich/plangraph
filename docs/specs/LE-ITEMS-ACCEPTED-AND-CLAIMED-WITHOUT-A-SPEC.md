## Decisions

- D1. Gate `lane` only, including an omitted kind. Use one canonical stem `docs/specs/<ID>` in the item's registered project repository, with the current canonical item ID after alias resolution and exact case. The expected files are `.md`, `.card.yaml` and `.tree.tsv`. Require all three to be nonempty regular Git blobs (mode `100644` or `100755`) at the same immutable commit. Git is the authority for existence. Accepted design content and card schema remain the planning review's responsibility. Generic `design_ref`, note `files`, DB cards and uncommitted files grant no admission.
- D2. New definitions must supply exactly one of `"spec_ref":{"path":"docs/specs/<ID>.md"}` or `"needs_spec":true`. The reference may add `"lane":"lane/<name>"`, which selects the matching remote-tracking branch for define only. A placeholder enters ordinary `open` state and is classified from main on every live ready or claim. Store neither request field and add no item state, column, backfill, grandfather list or edit flag. An accepted set on main lifts the spec block automatically.
- D3. Use the keeper Git adapter's existing repository registration and Git object store. The keeper's existing work-index refresh fetches `origin` and publishes its remote-tracking refs. The local mirror can be bare. Ordinary work claims require a successfully refreshed `refs/remotes/origin/main` and a complete set at its tip. Reuse the existing preflight, deadline, batch sharing, error envelope, audit and claim transaction. A named-lane reference never satisfies claim or ready.
- D4. The planning queue covers every governed open lane missing its main proof, including lanes with unfinished implementation dependencies. Its plan parents are live same-project `gate` rows with a direct `depends_on` edge to the lane. Include the lane under each such gate and once in the flat list. Use a null parent for orphaned work. `project` filters the queue. `n`, `owner`, `mine` and `agent` still filter or cap their existing ready results and do not cut the planning inventory.
- D5. The planning session authenticates as a dedicated project-scoped L1 principal registered to the live parent gate in keeper config. A single `claim` with `spec_for:<gate-key>` grants spec authoring under that plan and returns an audited authorization without an implementation lease. The item stays open and visible in the queue. The plan already has one designated planning session, so repeat calls by that principal grant the same operation. Normal, batch and phase-worker claims never inherit the planning exception from a principal's role alone.
- D6. Stage activation using the keeper configuration. Activate across all projects in the keeper instance together, including projects with unavailable mirrors. Before activation, ensure a nonempty set of runnable, spec-backed lanes for work that must continue and configure the real planning bindings. Already active implementation leases and review lifecycles keep their existing rights. Any later ordinary claim requires current proof, and the phase-worker payload path checks proof even when reusing a lease.
