## 2. Self-hosted runner security on public repos (GitHub official)

- "Self-hosted runners should almost never be used for public repositories", because anyone can open a PR and compromise the environment; they are not guaranteed ephemeral clean VMs and can be persistently compromised. sourced (https://docs.github.com/en/actions/reference/security/secure-use, no date on page).
- Add-runners docs: "only use self-hosted runners with private repositories"; forks can run dangerous code on the runner. Runner groups: public repos cannot use a group's runners by default (can be overridden). sourced (https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners, no date).
- Fork PR approval (Settings > Actions > General), three options: first-time contributors new to GitHub; first-time contributors (DEFAULT); ALL external contributors. Approval needs write access. Under the first two, any contributor with one previously merged PR runs without approval (attack: land a trivial PR first). `pull_request_target` always runs regardless of these settings. The page explicitly says that on self-hosted runners approved/bypassed workflows execute user-controlled code automatically. sourced (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository, no date).
- JIT runner REST endpoint `generate-jitconfig` exists and has an `ephemeral` field, but the REST page does not define ephemeral semantics. sourced (https://docs.github.com/en/rest/actions/self-hosted-runners). The ARC doc warns shared clusters for production are risky because workflows run arbitrary code (https://docs.github.com/en/actions/tutorials/use-actions-runner-controller/deploy-runner-scale-sets).
- Larger runners with static IPs: GitHub advises using them only with private repositories because forks can run dangerous code. sourced (https://docs.github.com/en/actions/how-tos/manage-runners/larger-runners/manage-larger-runners).

## 3. Fastest options (by evidence)

- Raw speed: the 32-thread self-hosted workstation beats everything here (hosted choices top out at 4 vCPU free on GitHub, 4 vCPU free on GitLab Free, up to 8 vCPU on CircleCI OSS). Third-party "2x faster" claims are vendor marketing (unverified); no independent benchmark was fetched.
- Fastest FREE hosted for public repos: GitHub standard 4 vCPU/16 GB, 20 concurrent jobs (sourced above). Everything faster than that costs money or needs a free-minute allowance (Blacksmith 3,000 min, Ubicloud 1,250 min, both short of unlimited).
- Free third-party that can be bigger than 4 vCPU at no vendor charge: RunsOn and Cirun OSS plans (but you pay AWS/cloud), and GitLab for Open Source (up to 32 vCPU sizes with 50,000 min, requires hosting the project on GitLab).

## 4. Recommendation (5 lines)

1. Default for the public repo: GitHub-hosted `ubuntu-latest` (4 vCPU/16 GB, free and unlimited, 20 concurrent) for ALL pull_request jobs from forks.
2. Keep the 32-thread workstation only for trusted events (push to main/tags, same-repo branches), as an ephemeral/JIT runner in a throwaway container or VM, on a separate runner group and label that public forks cannot target; never expose it to `pull_request` from forks or `pull_request_target`.
3. Set fork-PR approval to "Require approval for all external contributors" and keep default `GITHUB_TOKEN` read-only; no long-lived secrets on the workstation.
4. If you need more speed for public PRs without self-hosting: apply to Blacksmith OSS (check org-only limitation) or run RunsOn/Cirun OSS in your own cloud account; ignore dead services (Cirrus CI, BuildJet) and Azure public projects (retired).
5. Re-check before going public: the postponed self-hosted $0.002/min charge (private repos only so far) and whether plangraph lives in a personal account or an org (Blacksmith and GitHub larger runners need an org).
