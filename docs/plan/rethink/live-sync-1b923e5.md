## 4. Restart runbook for build-L1 (after router GO; not executed here)
1. Check out T (1b923e5) to a tree; edit the unit's WorkingDirectory/PYTHONPATH only (keep a copy of the unit).
2. `systemctl --user stop plangraph-keeper` first and confirm `is-active` = inactive and `fuser keeper.db.lock` empty before the backup: the daemon holds the flock `keeper.db.lock`; `.backup` of a stopped db also folds WAL. Then
   `sqlite3.Connection.backup` keeper.db -> dated 0600 file (a `.backup` call is WAL-safe; a plain cp needs -wal/-shm too), copy keeper.json and plan.snapshot.json(+.sig) beside it.
3. Start the unit (the migration runs in `open_db`, single-writer under the lock, so no concurrent-migration race; do NOT run `pg admin migrate` against the live db while the daemon runs).
4. Verify: `pg admin verify` = chain and cache integrity ok; `pg admin verify-snapshot` ok after the first write; whoami/ready/percent rc=0; `GET /inbox` 200. Row counts: compare with the step-2 backup only before clients reconnect (items/events/audit_log legitimately grow once writers replay or heartbeat); the invariant is that no ORIGINAL row disappears: counts >= backup counts, chain ok.
5. Half-migration: `open_db` runs several idempotent scripts without one enclosing transaction; if the daemon is killed mid-start, just start it again (IF NOT EXISTS completes the rest); a startup OperationalError about a missing table = start again once before aborting. To avoid a `Restart=on-failure` loop, if the second start also fails run `systemctl --user stop plangraph-keeper` before investigating.
   Never run a WRITING `pg admin` command (migrate, init, add-principal, import, revoke) while the daemon is up; read-only `admin verify` / `verify-snapshot` are fine; check `systemctl --user is-active plangraph-keeper` first.
   Abort = any verify failure, daemon exit/restart loop, or an original row disappearing: restore in this exact order: (a) `systemctl --user stop plangraph-keeper` (an explicit stop is not undone by the unit's `Restart=on-failure`, but confirm with `is-active` and that no process holds keeper.db.lock: `fuser keeper.db.lock` prints nothing); (b) delete keeper.db-wal and keeper.db-shm from the data dir BEFORE placing the backup (a leftover WAL, including from a half-finished migration, must never meet the restored file; if the daemon was killed mid-migration the WAL is deleted too, and the restored backup is a complete pre-migration db); (c) copy back the step-2 db, keeper.json and plan.snapshot.json(+.sig); (d) repoint the unit at f3bac63; (e) start, then `pg admin verify` and `pg admin verify-snapshot`.
   Code-swap rollback (no restore) is allowed ONLY if T wrote nothing since start; any design-3 write (state_set, questions/answers, cards, attempts, decisions) means restore the backup. The only event type T adds to `EVENT_TYPES` is `state_set` (git diff schema.py; `run_recorded` etc. predate f3bac63). Only `state_set` was proven to break old verify; the other design-3 writes were not tested against old code, so that part is deliberately conservative. Ordinary claim/heartbeat/release/define events are the old event types and were proven compatible (old code defined an item on a T-migrated copy; verify ok); T writing only those does not force a restore, but the doc does not require telling them apart, so default to restore when unsure.
6. Outbox is client side (`PG_OUTBOX`/`pg replay` on writer hosts) and untouched; clients queued during the stop replay after start.
