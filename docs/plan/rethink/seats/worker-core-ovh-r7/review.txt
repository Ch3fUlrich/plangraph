**V2 – Completeness of `check_rev` guarding**

*All git‑invoking entry points that accept a user/card‑derived revision now call `check_rev` **before** the argument list is built, and the command line is terminated with `--` where a revision appears at the end.*

- `confine.rs:changed_files` – `check_rev(base)?; … git(..., &range) …`
- `confine.rs:diff_hash` – `check_rev(base)?; … git_bytes(..., &["diff", "--binary", "--output=-", &range]) …`
- `worktree.rs:create` – `check_rev(base_sha)?; … git(..., &["worktree", "add", "-q", "-b", &id.branch(), "--", &dest_s, base_sha])`
- `janitor.rs:commits_beyond_branch` – `check_rev(base)?; … git(..., &["rev-list", "--count", &format!("{base}..{branch}")])`
- `probe.rs:commits_beyond` – `check_rev(base)?; … git(..., &["rev-list", "--count", &format!("{base}..HEAD")])`

There are no remaining public functions that forward a raw revision string to `git` without this guard. All places where a *branch* name derived from a card ID is supplied use the `-b` flag (which does not treat the value as a bare revision) and are therefore safe from option‑injection.

**Result:** The rev‑validation is complete; no injection path remains.
