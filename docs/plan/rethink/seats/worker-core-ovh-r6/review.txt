**V2 – completeness of the `check_rev` guard**

All public functions that accept a user‑supplied revision string now invoke `check_rev` before any `git` command that could treat the string as an argument:

| File & function | Guard added |
|---|---|
| `rust/worker-core/src/confine.rs:changed_files` – adds `check_rev(base)` before building the diff range. |
| `rust/worker-core/src/confine.rs:diff_hash` – adds `check_rev(base)` before calling `git_bytes`. |
| `rust/worker-core/src/janitor.rs:commits_beyond_branch` – adds `check_rev(base)` before the `rev-list` call. |
| `rust/worker-core/src/probe.rs:commits_beyond` – adds `check_rev(base)` before the `rev-list` call. |
| `rust/worker-core/src/worktree.rs:create` – adds `check_rev(base_sha)` before the `git worktree add …` invocation and also inserts `--` to terminate options. |

`check_rev` (in `rust/worker-core/src/git.rs`) rejects empty strings, strings starting with `-`, and any string containing whitespace or control characters. The only other places where a revision can reach `git` are internal uses (e.g. `git rev-parse HEAD`) that are not derived from external input, so there are **no remaining injection vectors** such as branch‑name construction from card IDs or unchecked refspecs.

**V4 – deferred items (symlink sandbox) and the two noted gaps (24 h wait cap & probe‑fail backoff)**  

* The symlink‑escape concern is about **runtime file‑system writes** performed by the harness that runs the worker, not about the core logic in `worker‑core`. Since the core only inspects Git‑tracked paths, the safety boundary is enforced upstream; deferring to the Temporal glue lane (RT‑P1‑WORKER) is appropriate.  

* The *24 h wait cap* and *unbounded probe‑fail backoff* are part of the **budget / retry scheduler**, which lives in the Temporal glue lane (see the design note at the end of `REVIEW‑R2.md`). They do not affect any public API of `worker‑core`, nor do they introduce security or correctness issues inside this crate. Hence, deferring their implementation to the glue lane is acceptable.
