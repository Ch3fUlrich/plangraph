## V1: Migration Safety

The idempotent migration-on-open is structurally adequate for normal operation but has a partial-failure window not addressed in the doc.

**Grounded adequacy:**
- `db._upgrade` (src/plangraph/keeper/db.py) uses `CREATE TABLE IF NOT EXISTS` and `CREATE TRIGGER IF NOT EXISTS` throughout DESIGN3_DDL, so re-running is safe (confirmed empirically in doc §5: "migrate ran 3x… all 'schema up to date'").
- No existing tables are altered: `_ADDED_COLUMNS` is described as unchanged, and the new objects are all new tables/triggers/indexes. The `ALTER TABLE ... ADD COLUMN` loop would be a no-op on already-migrated columns.
- `daemon.run` (src/plangraph/keeper/daemon.py) acquires the exclusive flock via `lock_keeper` BEFORE calling `open_db`, so two daemons cannot race the migration. `busy_timeout` defaults to 5000 ms (`_DEFAULT_BUSY_MS`).
- The doc correctly prohibits `pg admin migrate` against the live db while the daemon runs.

**Defect (groundable):** `_upgrade` executes five sequential `conn.executescript(...)` calls (`ALIASES_DDL`, `RUN_TOKENS_DDL`, `OUTBOX_DDL`, `DESIGN3_DDL`, `PROJECTOR_SQLITE`) without an enclosing transaction. `isolation_level=None` (line visible in `open_db`) puts every statement in autocommit. If the process is killed between, say, `OUTBOX_DDL` and `DESIGN3_DDL`, the database is in a half-migrated state. Recovery is possible (next `open_db` re-runs the missing scripts under IF NOT EXISTS), but the doc's "idempotent, DML-free" framing implies atomicity it doesn't have. Speculation risk is low (the window is milliseconds), but the runbook (step 5 abort criteria) does not list "daemon startup fails with missing-table OperationalError" as a known half-migration symptom, and no explicit "just restart" guidance appears.

## V2: Rollback Claim

The doc's claim—"code-swap rollback is safe only until T writes a design-3 `state_set` event; after that restore backup"—is **directionally correct but incompletely specified**.

**What the excerpts confirm:**
- `events.py` line 247: `elif kind == "state_set"` is a new projector branch. The old code at f3bac63 lacks this branch. `store_cards.set_state` appends event kind `"state_set"` and updates the `items` row. Old replay does not fold it → `cache_mismatch` (empirically confirmed in the log's rollback section: `{'code': 'cache_mismatch', 'field': 'state', 'expected': 'open', 'got': 'parked'}`).
- New tables (cards, attempts, questions, etc.) are invisible to old queries.
- Old code serves fine on a T-migrated copy **until** `state_set` is written.

**Incompleteness (groundable from doc §3 + code):**
- The rollback trigger should be "any write verb that produces an event kind unknown to the old projector on an existing item." The doc only names `state_set` → `set_state`. No other new event kind is visible in the excerpts, so within the provided material the claim is correct. However, the doc does not prove that no other code path in T appends an unrecognized event on existing items (e.g., a "card_linked" event touching an item's event stream). This is **speculative risk**, not a code-grounded defect.
- The rollback instruction ("stop keeper, restore backup db and json, start f3bac63") is correct, but the doc does not mention that the restored WAL sidecars must be cleaned up or replaced. `sqlite3.Connection.backup` produces a single file; if stale `-wal`/`-shm` files remain from the T run, old code opening the DB may replay WAL frames into it, re-introducing the `state_set` rows. The doc's own step 4 runbook warns about this for backup (`"a plain cp needs -wal/-shm too"`), but the rollback path in section 3 omits the equivalent cleanup instruction.

## V5: Restart Runbook (doc §4)

**Ordering is correct:** checkout T → edit unit → stop daemon → backup → start → verify → (abort if needed).

**Defect — spurious abort from client replay race:**
Step 4 requires "table counts (10 originals) equal the pre-restart counts." Step 6 states "clients queued during the stop replay after start." Between step 3 (daemon starts, serving) and step 4 (operator runs count check), outbox clients on writer hosts will reconnect and replay. This increments `items`, `events`, `audit_log`, and possibly `principals`. Step 5's abort criterion is "original-table count change." The runbook will **falsely abort** if even one client replays a queued write during the verify window. The doc does not include a step to hold clients (e.g., block firewall, set a maintenance gate) or to exclude client-replay deltas from the comparison. This is grounded in the tension between step 6's description and step 4's requirement.

**Other runbook observations:**
- Step 2's backup procedure is correct: stop → `.backup` (folds WAL) → copy json/snapshot. No step would harm the live db.
- Step 3 correctly warns against running `pg admin migrate` while daemon holds the lock.
- Step 5 abort path ("restore step-2 backup, repoint to f3bac63, start, verify") is sound, but inherits the V2 WAL-cleanup gap (see above).
- No step to delete or quarantine stale `-wal`/`-shm` files after restoring the backup. If `.backup` was done while clean, this shouldn't apply—but if the restore target already has `-wal` files from the aborted T run, SQLite could replay them.

**No step would actively corrupt the live db.** The procedure uses `sqlite3.Connection.backup` (WAL-safe, per doc) and the daemon is stopped first.
