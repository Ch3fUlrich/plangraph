**V1 – Migration safety**

*Idempotence & data loss* – `db._upgrade` (src/plangraph/keeper/db.py:_upgrade) only adds missing columns (`ALTER TABLE … ADD COLUMN`) and runs `CREATE … IF NOT EXISTS` scripts.  All DDL is DML‑free, so no existing rows are modified or deleted.  The migration therefore cannot lose user data.

*Lock & concurrency* – The daemon acquires an exclusive lock via `kdb.lock_keeper` before calling `open_db` (src/plangraph/keeper/daemon.py:run).  While the lock is held the process is the only writer; other processes can only read.  Consequently the migration will not race with concurrent writers.  The only conceivable race is if another process holds a **different** lock file (e.g., a stray CLI) – the default `busy_timeout` (5 s, src/plangraph/keeper/db.py:_DEFAULT_BUSY_MS) means the migration will wait, then fail with a timeout rather than corrupting the DB.  This is acceptable but should be documented.

*Partial‑upgrade window* – `_upgrade` executes a series of independent statements without an outer transaction.  If the daemon is killed after some `CREATE TABLE` statements but before the rest, the DB ends up in a partially‑upgraded state.  A subsequent start will simply re‑run the missing statements (`IF NOT EXISTS` protects already‑created objects), so the DB will converge to the final schema.  No data loss occurs, but the runbook’s “half‑migration” note (section 4) is the only mitigation; the doc correctly calls out this scenario.

*Backup procedure* – The runbook recommends using `sqlite3.Connection.backup`, which is WAL‑safe (the same method used in the dry‑run).  The documented plain‑`cp` warning is accurate.  No other backup steps are required.

*Overall* – The migration is safe with respect to data loss and consistency, provided the exclusive lock is respected.  The doc’s claim is largely correct; the only missing nuance is the need to tolerate a half‑finished `_upgrade` if the process crashes mid‑start (speculative risk, already mentioned in the runbook).

**Conclusion:** the rollback statement is correct and complete within the evidence; the conservatism is justified.

**V5 – Restart runbook (section 4)**

*Ordering*: Stop → backup → swap → start → verify – matches the safe sequence for SQLite WAL.

*Verification steps*: `pg admin verify` and `pg admin verify‑snapshot` are required; the runbook also suggests confirming basic API health (`whoami`, `GET /inbox`).  This is sufficient.

*Abort criteria*: Any verify failure, daemon exit/restart loop, or disappearance of original rows triggers a restore.  The definition is clear.

*Potentially harmful step*: Deleting `keeper.db‑wal` and `keeper.db‑shm` **before** restoring the backup (step 5(b)).  If performed while the daemon is still holding the lock or if a WAL file from a half‑finished migration is removed prematurely, the restored database could become inconsistent.  The runbook does warn to stop the unit first, but the ordering could be made explicit (stop → delete WAL/SHM → copy backup).  This is a minor clarification, not a defect.

*Missing checks*: The runbook does not verify that the lock file (`keeper.db.lock`) has been removed after the stop, nor that a new lock is created on start.  In practice systemd will clean it, but an explicit check would eliminate a possible start‑failure scenario.  (Speculative.)

*Overall* – The runbook is sound; only the WAL/SHM deletion step could be emphasized more clearly.
