# V1: Migration Safety

**Idempotent open_db._upgrade is adequate for the DDL-only changes shown.** The `_ADDED_COLUMNS` loop guards each ALTER with `PRAGMA table_info`, and all subsequent scripts use `CREATE TABLE IF NOT EXISTS` / `CREATE TRIGGER IF NOT EXISTS` (schema.py DESIGN3_DDL lines 50, 57, 70, 89, 115, 131, 151, 158, 167, 174, 186, 193). With `isolation_level=None` (db.py open_db line 38), each statement autocommits, so partial failure leaves no transactional corruption; re-running is safe.

**Lock ordering is correct.** `daemon.py:run` calls `lock_keeper` before `open_db`, so `_upgrade` executes while the exclusive flock is held. No other writer can race.

**Grounded defect:** The doc states `_upgrade` is "DML-free" and this is true for the shown code, but the doc's own statement "No existing table altered; no ALTER on existing columns" is misleading. `_upgrade` iterates ALL of `_ADDED_COLUMNS` (db.py line 99-102) and would issue ALTERs on the `items` table if columns were missing. The correct claim is "`_ADDED_COLUMNS` is the same list in f3bac63 and T, so no new ALTER targets are introduced" — which is what the parenthetical means, but a reader skimming could misinterpret.

**Backup procedure:** The doc correctly requires stopping the daemon before `.backup` (WAL checkpoint on stop) and explicitly warns against running `pg admin migrate` while the daemon is up. No defect here.

**Concurrency with other readers:** In WAL mode, read-only clients (e.g., `GET /inbox` handler) can operate during short DDL no-ops. No evidence of a writer-side lock escalation that would block the daemon's own `_write()` path during migration; migration completes before `server.start()`.

# V2: Rollback Claim

**The claim is internally inconsistent across sections 3 and 4.**

Section 3 (rollback rehearsal): "rollback via code swap is safe **only while T has written no design-3 state/cards/attempts/questions**" — this limits the dangerous condition to new event types and tables.

Section 4 (abort/rollback criteria): "Code-swap rollback (no restore) is allowed ONLY if T wrote nothing since start; any T write (state_set, questions/answers, cards, attempts, **normal claims**) means restore the backup." — this adds "normal claims" to the trigger.

**Grounded defect (moderate):** The evidence supports only `state_set` breaking old verify (`events.py:247` folds `state_set` into `item["state"]` as a new event kind; old code has no handler for it, producing cache_mismatch). Normal claims use pre-existing event kinds that old `events.py` folds correctly. The doc acknowledges this ("Only state_set was proven") but then states the broader rule as fact. A runbook reader following section 4 would over-restore (losing hours of writes for a condition that provably can't happen). The correct rule is the narrower one in section 3; the wider rule is **speculation** dressed as policy.

**Completeness gap:** The doc does not mention that restoring the backup also reverts any **normal** writes (claims, heartbeats, defines) that occurred while T was running — data loss proportional to T's uptime. Section 4 step 4 notes this ("every write since T's first start is lost on backup restore") but the rollback procedure (step 5 a-e) doesn't repeat this warning at the point of action. A panicked operator might not connect the steps.

**WAL handling in rollback:** Step 5(b) "delete keeper.db-wal and keeper.db-shm BEFORE placing the backup" is correct and grounded — if a stale WAL from T's writes meets a restored pre-T db, SQLite may replay those pages. No defect.

# V5: Restart Runbook (Doc Section 4)

**Ordering:** stop → backup → swap tree → start → verify. Correct: the stop before backup ensures WAL checkpoint and no concurrent writer. The doc says to verify with `is-active` and confirm no lock holder. No defect.

**Step 3:** "do NOT run `pg admin migrate` against the live db while the daemon runs." Correct — open_db calls _upgrade which acquires the write lock via SQLite. A competing CLI migrate would block on busy_timeout (5000ms, db.py `_DEFAULT_BUSY_MS`) and then fail.

**Step 4 verification:** Running `pg admin verify` while the daemon is active is safe because _upgrade is all no-ops after first migration (columns exist, IF NOT EXISTS) and the verify query path only reads. WAL mode permits concurrent readers. No defect.

**Step 5 half-migration guidance:** "start it again (IF NOT EXISTS completes the rest)" — correct per code analysis. "a startup OperationalError about a missing table = start again once before aborting" — correct: if PROJECTOR_SQLITE creates tables that _upgrade_lock_triggers references, and the process is killed between them, a missing-table error is expected on retry because _upgrade re-runs the full sequence idempotently.

**Abort criteria:** "any verify failure, daemon exit/restart loop, or an original row disappearing" — sound.

**Grounded concern (low severity):** Step 5(a) says "confirm with `is-active` and that no keeper.db.lock holder remains." The doc correctly identifies this check. However, `lock_keeper` uses an OS-level flock (visible via `fuser` or `/proc/locks`), not a PID file. The doc doesn't specify HOW to confirm no lock holder remains. This is operational detail that could matter on a machine with stale file descriptors, but is not a logical defect in the runbook.

**No step harms the live db.** The backup is read-only (`.backup` ro URI), the migration is idempotent DDL, and the rollback procedure correctly deletes WAL/SHM before placing a backup copy (preventing WAL replay against restored data).
