## V5 Restart Runbook (Section 4)

**Ordering:** Prepare unit → stop daemon (release flock) → `.backup` of stopped db + configs → start unit (migration fires in `open_db` under lock) → verify → clients reconnect. This is correct: stop-before-backup avoids WAL mid-write; start-after-backup means the backup is a clean pre-migration snapshot.

**Verification:** `pg admin verify` (chain+cache), `pg admin verify-snapshot`, read verbs, `/inbox` 200, row counts ≥ backup. Invariant stated: "no ORIGINAL row disappears." Adequate.

**Abort criteria:** Any verify failure, daemon exit/restart-loop, or original-row disappearance triggers restore. Restore order: stop → confirm no fuser → delete -wal/-shm → copy backup → repoint unit → start → verify. This is correctly ordered and avoids the WAL-meets-restored-file corruption class.

**Harm to live DB:** Step 5's deletion of `-wal`/`-shm` occurs only after confirming daemon is stopped and `fuser` reports no holders. Safe. The `open_db` call sets `journal_mode=WAL` before `_upgrade` — WAL must be available at the target path. If the filesystem rejects WAL (e.g., NFS without advisory locks), `conn.execute("PRAGMA journal_mode=WAL")` would silently fall back to `delete` mode (SQLite behaviour), but the doc doesn't mention filesystem requirements. **Speculation only — not grounded in an excerpt defect.**

**Half-migration recovery:** "Start again" relies on idempotent DDL. The doc covers OperationalError-about-missing-table. If the failure mode were `SQLITE_BUSY` (another writer grabbed a table lock), the fix is the same (restart). The doc says "start again once before aborting" — reasonable.

**No defect found.**
