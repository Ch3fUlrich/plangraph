The batch step runner has real claim, ci_class and train_join actions (`step_services`): claim runs the keeper `claim-batch` for every item and, when one is refused, releases only the epochs it was granted (a failed release is reported), ci_class reads the workflow runs of the pushed head that belong to the pull request and classifies them green (every required workflow has a passing run; a skipped one is no evidence) or red (naming the failing run), and train_join passes the consumed CI run to the site's train desk command. The service calls are traits with command-backed implementations, so a fake keeper and CI run a batch to train join in tests. The shell fast-checks step refuses an empty check list.
