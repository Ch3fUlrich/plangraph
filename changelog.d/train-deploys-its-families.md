- A landing train deploys what it merged. `plangraph land-train deploy-plan` now derives the families of a built train or of a landed range (`--base --head`) from the train-wide landed paths, through `deploy/manifest.toml`: a unit file maps to its family, any file of a crate to every deployed binary of that crate and of the crates that depend on it; a merge resolution and a stacked edit of a binary an earlier part added both ship, with the later part's item and host. Hosts come from item `Deploy-Hosts`, commit `Deploy:` trailers, else the hosts holding the manifest roles (`--role-hosts`, or `PG_HOST_ROLES` in the host registry). Families the train cannot install (not deployed, system units, rendered templates, binaries host-sync does not build) are listed as skipped with the reason. New: `deploy-apply` (dry run by default; `--mode apply` installs each target through `deploy-host` on its host, checks the first run and records keeper deploy rows through `--row-cmd`, resumable from its state file), `deploy-host` (the host side: check, install, read, disable; `check` is the install dry run printing `MISSING` lines) and `deploy-train`, which train settlement runs before merge-close (`PG_LAND_DEPLOY=apply` installs; otherwise a dry run that never stops settlement). The keeper CLI takes a deploy row with `evidence KEY --kind deploy --ref JSON`.
