# Review of KEEPER-LIVE-SYNC Plan: f3bac63 → T=1b923e5

## V1 — Migration Safety

**Idempotent CREATE IF NOT EXISTS on every open_db**

The approach is adequate in the common case but carries two non-trivial risks the doc understates:

1. **DDL lock contention on a live WAL writer.** `CREATE TABLE IF NOT EXISTS` and `CREATE TRIGGER IF NOT EXISTS` acquire the write lock briefly (SQLite takes a RESERVED/EXCLUSIVE lock for any schema DDL). On a WAL-mode db with an active writer, the first `open_db` call at daemon startup will block until the in-flight transaction commits or until the busy_timeout expires. If the previous process didn't exit cleanly (crash, SIGKILL before `lock_keeper` release), the operator will see a startup hang rather than a schema error. The doc should state an explicit `busy_timeout` value and a hard timeout for the migration step.

2. **Trigger idempotency is asserted but not evidenced.** The doc says "idempotent CREATE IF NOT EXISTS" as a blanket statement. `CREATE TRIGGER IF NOT EXISTS` is valid SQL in SQLite ≥ 3.3.0, but the dry-run never re-runs migration on an already-migrated db with triggers present (step 2's "migrate again" shows `schema up to date` only for tables, not for triggers). If the implementation uses bare `CREATE TRIGGER`, a second open_db will crash. A targeted test—run migration twice, confirm no `OperationalError: trigger already exists`—is needed.

**No version table / no user_version.** Operationally this is a correctness risk, not a data-loss risk: there is no way to detect a partially-migrated state (e.g., process killed after 4 of 9 new tables created). Because DDL is idempotent this self-heals on next open, but it means the operator cannot distinguish "migration not yet run" from "migration completed" without inspecting `sqlite_master` manually. For a production daemon this is acceptable but should be noted in the runbook.

**events.append seq assignment change.** Replacing AUTOINCREMENT with explicit max+1 logic is functionally equivalent on SQLite (AUTOINCREMENT only guarantees monotonicity, not gaplessness). The doc's claim "same numbering" holds as long as no concurrent writer interleaves between the max-read and the INSERT. Inside `lock_keeper`'s exclusive section this is safe. The doc should explicitly state that the read+assign is within the same write transaction (it presumably is, but it's not called out).

**Backup procedure.** `sqlite3.Connection.backup` from a read-only URI source is correct for WAL and is the right choice over `cp`. One gap: the doc says the backup is taken "before restart" but doesn't say the old keeper must be fully stopped (lock released) first. `sqlite3.Connection.backup` opens the source in read-only and does not require the source process to be idle, but a concurrent writer can cause the backup to take the pre-transaction snapshot, meaning the backup does not include the last committed transaction if the timing is unlucky. Best practice: stop daemon → take backup → swap code → start.

**No data-loss risk from the migration itself.** No ALTER, no column removal, no DROP. The 10 original tables are untouched (confirmed by row-count parity). This part is sound.

## V2 — Rollback Claim

The doc's core logic is correct: once T writes a `state_set` event that changes an item's state to a design-3 value, old code's cache-rebuild produces `cache_mismatch` because it doesn't know the new states. The dry-run confirms this empirically (the `parked` mismatch).

However, the rollback procedure is **incomplete** in several respects:

1. **Data-loss window is unquantified.** "Restore the pre-restart backup" means every event, item, outbox entry, and state change committed after T's first open_db is lost. The doc never states this explicitly to the operator, nor does it describe a re-apply procedure. For a production system this could be minutes to hours of lost work depending on how long the new code runs before rollback is triggered.

2. **Outbox gap.** The dry-run shows `outbox_seen 0` and `replay` reports "no outbox", so outbox isn't exercised. If T populates an outbox or `outbox_seen` (which the schema has a table for), restoring the backup discards those entries. The doc doesn't mention this. If outbox drives downstream signal delivery (Temporal), a rollback could mean duplicate or lost signals to external systems.

3. **Snapshot signature / hash chain anchors.** `verify-anchor` returned "anchors not configured"—this means the live system has no external anchor. If T writes new events (even non-design-3 ones with the explicit-seq change), the hash chain format is unchanged per the doc, so old code's chain verify should pass. But the doc doesn't test this direction: old code verifying a chain extended by T's explicit-seq events. The dry-run only verifies the chain *before* rollback and *after* restoring the backup—never with the T-modified db opened by old code post-seq-change. The `cache_mismatch` test used a state change, not a seq anomaly.

4. **The backup must include the signing key state.** Restoring keeper.json is mentioned but the signing key is referenced "by path." If T rotates or modifies any key-derived state (snapshot pubkey validation), restoring json alone may not suffice. Low risk given the doc says keys are unchanged, but should be called out.

5. **No abort criteria definition.** The doc describes *how* to roll back but not *what signals* should trigger the rollback decision post-restart. Is it the first `cache_mismatch` in verify? A specific exception? Daemon refusing to start? This belongs in V5 but is a rollback-claim completeness issue: the operator needs a decision procedure, not just a mechanism.

## V3 — Dry-Run Coverage

The doc honestly lists what wasn't exercised. I'll assess the materiality of each gap plus things the doc *claims* were tested but the log contradicts or weakens:

**Gaps that could break production restart:**

- **`changelog` rc=2 in the log.** The doc lists `changelog(--since 0)` under "read verbs rc=0," but the log clearly shows a bare `changelog` call returning `rc=2 bytes=117`. This means the verb without `--since` fails. If any production automation or health-check invokes `pg changelog` without `--since`, it will error post-restart. The doc's summary is misleading—this was not a uniform rc=0.

- **`verify-snapshot` rc=1.** In run1, `admin verify-snapshot` returns rc=1 (the doc says "signature ok after first write" but the log shows a failure before the write and a pass after—run2 passes). This implies the pre-existing snapshot is *invalid* under T's verification code. If the operator restarts and the first thing they check is snapshot validity (as part of "verify everything is good"), it will fail until the next snapshot write. The doc should flag this timing gap.

- **`sync pull` rc=1.** Doc says "not applicable" but the command was exercised and failed. If any CI or cron job invokes `sync pull`, it will break. The "not applicable" framing hides a real failure mode.

- **`set-kind` and `evidence` on nonexistent items.** Doc claims "usage paths" tested, but the log shows only `rc=2` (not found) with no positive-path test. If these verbs have new code paths (they touch design-3 tables), the happy path is completely unexercised.

- **Triggers.** The append-only triggers on `attempts/decisions/answers` were never written to. A trigger bug (e.g., wrong column reference) would only surface on first production write to those tables.

- **Postgres lazy imports.** The doc claims "system python3 starts fine without psycopg" but never verifies that the daemon doesn't accidentally import pg modules on a non-pg code path. If `daemon.run` or `open_db` has a conditional import that depends on `backend` config key parsing (rather than the value being absent), a malformed config could trigger an ImportError at startup.

- **Temporal signal.** Listed as untested. If `answer_question` has a code path that raises an unhandled exception when `TEMPORAL_ADDRESS` is unset, the `/v1/questions` POST endpoint could 500. This is only "safe" if the doc's claim "failure never fails the answer" is structurally verified.

- **`/inbox` POST, PUT, DELETE, sub-paths.** Only `GET /inbox 200` was tested. An unauthenticated static endpoint with other methods could expose unexpected behavior (e.g., file listing, SSRF via form action, or a handler that triggers daemon logic).

**Verbs never exercised beyond `--help`:** submit, evidence, verdict, waive, withdraw, close, legacy, rehome, delegate, token. For a "live restart" these are lower risk (daemon doesn't call them), but if the daemon's HTTP surface routes to any of these internally (e.g., the Temporal signal path invokes `verdict`), they matter.

5. **No PostgreSQL DSN is shown** despite being discussed. Good.
6. The doc doesn't leak the `TEMPORAL_NAMESPACE` value or any Temporal connection details.

This is a minor information-disclosure for a threat model involving repo-read attackers, but is standard practice for internal ops docs.

**Verdict on hygiene: no leaks of actual secrets; acceptable.**

## V5 — Restart Procedure Gaps

The doc describes the *mechanism* (swap code, open_db triggers migration, backup for rollback) but lacks a proper **operator runbook**. Missing elements:

1. **Explicit ordering and stopping discipline.** The doc never states the sequence as a numbered procedure:
   - (a) Stop the old keeper (`systemctl stop` or equivalent) and confirm lock release.
   - (b) Take `sqlite3.Connection.backup` of live db + copy of live json.
   - (c) Swap WorkingDirectory/PYTHONPATH to T checkout.
   - (d) Start new keeper.
   - (e) Run `pg admin verify` within N seconds of start.
   - (f) Confirm `/v1/snapshot` responds 200 with auth token.
   - (g) Optionally: exercise one read verb.
   
   Without this, operators may: take backup while old daemon is mid-write (backup may miss last txn), swap code before stopping daemon (two processes fighting for `lock_keeper`), or skip the post-restart verify entirely.

2. **Verification after restart.** The doc implies `admin verify` should be run but doesn't specify a pass/fail criterion for "upgrade successful." What if verify reports the pre-existing snapshot mismatch (observed in dry-run)? What if verify reports the new empty tables as "anomalous"? The operator needs a list of expected outputs post-restart, not just "chain and cache integrity ok."

3. **Abort criteria.** No explicit triggers for "abort and rollback." Candidates:
   - Daemon fails to bind port within 10s → check backup/lock, restart old.
   - `admin verify` returns error code ≠ 0 within first 60s → rollback.
   - Unhandled exception in daemon log → rollback.
   - `/v1/snapshot` returns non-200 for authenticated request → rollback.
   
   These should be codified before the live restart.

4. **Graceful drain.** No mention of waiting for in-flight work items (claimed leases, running tasks) to complete or timeout before stopping the old daemon. If `heartbeat` is running on a 1h lease and the daemon is SIGKILL'd, the lease won't be renewed but the lock file may persist. The restart procedure should include "confirm no leases active" or "wait for lease expiry."

5. **`backup_prune` interaction.** Default is OFF—good. But if the operator's config accidentally includes `backup_prune: {enabled: true}`, the new daemon could prune the backup taken in step (b) within the same restart window, destroying the rollback path. The runbook should mandate: "verify backup_prune.enabled is false in the live config before restart" or "copy backup to a location outside the prune dir."

6. **Rollback execution detail.** "Stop keeper, restore backup db (and json), start f3bac63" omits:
   - Confirm new keeper is fully stopped and lock released before restoring.
   - Verify the restored backup's integrity (`PRAGMA integrity_check`).
   - Confirm the old tree checkout still exists or is re-fetched (what if the new checkout overwrote the old one in-place?).
   - Post-rollback verification (same steps as pre-restart).

7. **Monitoring window.** No guidance on how long to observe before declaring success. "If no errors in X minutes, the upgrade is complete" is needed.

---

## Overall Assessment

The doc is **largely correct** in its technical claims and the dry-run is credible. The migration mechanism is safe for the stated schema changes. The rollback logic is correct in principle. However, the doc has enough gaps (trigger idempotency untested, changelog/verify-snapshot/sync-pull failures under-described, restart runbook missing ordering and abort criteria, data-loss window in rollback unquantified) that I would not call it "ready for the operator without additions." The security posture is clean. The biggest practical risk is the operator executing the restart without a codified stop→backup→swap→verify→abort sequence.
