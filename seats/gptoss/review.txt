V1 – Migration safety  
File: src/lock_keeper.py function open_db → calls db._upgrade  
Evidence: “Migration = idempotent `db._upgrade` on every non‑create `open_db` (CREATE … IF NOT EXISTS, DML‑free). New tables … All empty after migrate. No existing table altered; no ALTER on existing columns.”  
Assessment: The CREATE‑IF‑NOT‑EXISTS style is safe under WAL when the writer obtains a brief RESERVED lock, but the doc does **not** guarantee that the upgrade runs before any other concurrent writer can start a transaction. Without an explicit exclusive lock or a busy‑timeout setting, a live daemon plus CLI tools could race, causing SQLITE_BUSY or a partially‑applied migration if a writer crashes mid‑operation. Backup via `sqlite3.Connection.backup` is performed only in the dry‑run; production rollback relies on a pre‑restart backup but does not mention copying the ‑wal/‑shm files. **Conclusion:** migration is likely safe for a quiescent system but lacks explicit concurrency safeguards; risk of lock contention or incomplete WAL backup exists.
