**V1 – Migration safety**

*Evidence*  
- `db.py:_upgrade` – iterates over `_ADDED_COLUMNS` and runs `ALTER TABLE … ADD COLUMN` only when the column is missing; then runs a series of `executescript(...DDL)` where all objects are created with `IF NOT EXISTS`.  
- `db.py:open_db` – calls `_upgrade` for every non‑create open, after acquiring the keeper lock in `daemon.run`.  
- `daemon.py:run` – obtains `kdb.lock_keeper` before `open_db`, guaranteeing an exclusive lock while migration runs.  
- `open_db` sets `PRAGMA journal_mode=WAL` and the backup procedure uses `sqlite3.Connection.backup`, which folds the WAL safely.

*Assessment*  
The migration is **idempotent and DML‑free**, so no existing rows are altered or deleted – no data loss.  The exclusive lock obtained by `lock_keeper` prevents concurrent writers from seeing a partially‑migrated schema, satisfying the concurrency requirement.  The backup step described in the runbook (`.backup` call) is safe for WAL databases.  

*Residual risk* – `_upgrade` runs several `executescript` calls **outside a single transaction**; if the daemon is killed exactly between those calls the database may be left with a subset of the new objects.  The runbook’s “half‑migration” paragraph acknowledges this and instructs a second start, but the risk should be highlighted as a migration‑restart edge case.

**V2 – Rollback claim**

*Evidence*  
- Rollback rehearsal (section 3 of the doc) shows that after a `state_set` event (`set_state` → `state_set`) the old daemon reports `cache_mismatch field=state expected=open got=parked`.  
- `store_cards.py:_set_state` creates a `state_set` event and updates `items.state`.  
- `events.py` folds `state_set` into the in‑memory item.

*Assessment*  
The claim **“code swap safe only until T writes design‑3 events … else restore backup”** is **correct for the `state_set` event** (the only design‑3 event proven to break the old verifier).  The doc conservatively extends this to all design‑3 types (cards, attempts, questions, etc.), but those were **not exercised** in the dry‑run; therefore the statement is **over‑broad** – it is correct for `state_set` but unverified for the others.  The recommended restore‑backup procedure (WAL‑safe `.backup` and removal of `-wal/-shm` files) is accurate.

**V5 – Restart runbook (section 4)**

*Ordering & verification* – The sequence **stop → verify lock release → `.backup` → copy config → start → verify** follows a sound pattern.  The runbook explicitly warns to delete `keeper.db‑wal`/`‑shm` before restoring, preventing stale WAL data from contaminating the restored database.

*Abort criteria* – Correctly defined: any verify failure, daemon restart loop, or disappearance of original rows triggers a full restore.

*Potential harmful step* – The only risky operation would be running a **writing `pg admin` command while the daemon is up** (the runbook warns against it).  If an operator mistakenly did so, the live DB could diverge from the backup, but the runbook’s prohibition mitigates this.  All other steps are safe for the live database.
