## V1 Migration Safety

The migration mechanism (`db.py:_upgrade`) is structurally sound: column adds are guarded by `PRAGMA table_info` checks, and all DDL statements use `IF NOT EXISTS`. The dry-run confirms idempotency (migrate ran 3x, step 5 says "schema up to date" each time).

**Defect — WAL fold is conditional, not guaranteed (doc sec 4 step 2):** The doc states `.backup` of a stopped db "also folds WAL." `sqlite3.Connection.backup` does not have special WAL-fold behavior beyond normal source-DB checkpointing. If the daemon is killed (SIGKILL, OOM) rather than stopped cleanly, no checkpoint runs; the -wal file retains committed transactions. The doc's own abort sequence (sec 5b) acknowledges this by mandating "delete keeper.db-wal and keeper.db-shm BEFORE placing the backup," but step 2 takes no similar precaution. If the backup is taken after an unclean stop (e.g., the stop in step 2 times out and the unit's `Restart=on-failure` kills the process), the backup may be missing recent WAL data, and restoring it later loses those transactions. The safe procedure would be to verify no -wal/-shm exist (or checkpoint them into the main db) before calling `.backup`.

**Adequate (grounded):** Concurrency is safe. `daemon.py:run` acquires `lock_keeper` before `open_db`. The doc correctly rejects the seat-raised concurrency race.

**Adequate (grounded):** No data-loss vectors exist. `_upgrade` is DML-free (the docstring states this and `_ADDED_COLUMNS` only ADDs columns; all DDLs are CREATE IF NOT EXISTS). Dry-run step 3 confirms row counts unchanged.

**Minor gap (speculation-level):** `_upgrade` calls `executescript` five times without an enclosing transaction. SQLite may hold an EXCLUSIVE lock during each `journal_mode=WAL` switch, causing other readers (if any bypass the flock) to hit the 5000ms `busy_timeout`. Given the flock design this is not a real concurrent writer, but the doc does not acknowledge the brief lock window.

## V5 Restart Runbook (doc section 4)

**Ordering (1→2→3→4→5→6):** Stop → confirm inactive + fuser empty → backup → swap unit → start → verify. Correct sequence. The fuser check before backup is good.

**Abort sequence (step 5):** stop → confirm → delete -wal/-shm → restore db/json/snapshot → repoint unit → start → verify. Ordering is safe (WAL must not meet restored db).

**Defect — fuser check does not cover the WAL/shm safety before backup:** Step 2 confirms the daemon is inactive and the lock is free, then immediately calls `.backup`. But it never checks for leftover keeper.db-wal / keeper.db-shm. Compare step 5b which mandates deleting them before restore. If the daemon crashed before the stop (unit state still "active" per systemd but process dead), `systemctl stop` may return success but -wal/-shm could be orphaned and contain uncheckpointed data from a prior session that the `.backup` API will not incorporate. Asymmetric handling between step 2 and step 5b.

**Defect — row-count invariant "counts >= backup counts" (step 4) does not flag the real risk:** The doc states the invariant is "no ORIGINAL row disappears." But `_upgrade` never deletes rows, and `daemon.py:run` starts a reaper (`server.start_reaper()`). If the reaper purges expired items (lease-expired rows), items count could drop below backup without any migration fault. The doc doesn't acknowledge the reaper as a legitimate row-reduction vector during the verification window. (Speculation on reaper behavior — the code excerpt only shows `start_reaper()` being called, not its implementation.)

**Harmful step:** None identified. The doc correctly prohibits writing admin commands while the daemon is up and correctly sequences the stop-before-backup.
